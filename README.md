# ordstat

Консольная утилита для аналитики интернет-магазина. Строит два JSON-отчёта:
1. **orders**: валидирует выгрузку заказов, записывает отклонённые строки в отдельный CSV, удаляет дубликаты, считает выручку в рублях, топ дней, топ городов, долю отмен по месяцам и находит подозрительные всплески заказов.
2. **logs**: потоково разбирает access-логи веб-серверов из разных часовых поясов, считает классы ответов, вычисляет перцентили времени ответа (p50, p95, p99) по нормализованным эндпоинтам и находит brute-force атаки по статусу 401.

## Установка и запуск

Требуется Python 3.12+. В рантайме используется только стандартная библиотека Python.

Установка пакета и инструментов разработки:

```bash
pip install -e ".[dev]"
```

Запуск отчёта по заказам:

```bash
ordstat orders --orders orders.csv --rates rates.json --aliases city_aliases.json --out orders_report.json --rejected rejected.csv --top-cities 10 -v
```

Запуск отчёта по логам:

```bash
ordstat logs --log access.log --out logs_report.json -v
```

Запуск через модуль Python:

```bash
python -m ordstat orders --orders orders.csv --rates rates.json --aliases city_aliases.json --out orders_report.json --rejected rejected.csv
```

## Структура проекта

* `src/ordstat/models.py`: иерархия исключений (`OrdstatError`), неизменяемые датаклассы (`Order`, `RejectedOrder`, `LogEntry`) и `TypedDict`-схемы отчётов.
* `src/ordstat/parsing.py`: потоковые генераторы чтения CSV и логов, загрузка JSON-конфигов, нормализация URL-путей и разбор строк лога.
* `src/ordstat/validation.py`: чистые функции парсинга и строгая 7-этапная валидация полей заказа.
* `src/ordstat/aggregations.py`: бизнес-логика дедупликации, агрегации метрик, метод двух указателей для окон в 600 секунд и расчёт перцентилей методом ближайшего ранга.
* `src/ordstat/report.py`: декоратор замера времени `@timed`, контекст-менеджер `RejectedCsvWriter` и сохранение JSON-отчётов.
* `src/ordstat/cli.py`: парсер аргументов `argparse`, настройка логирования и обработка кодов выхода (`0`, `2`, `3`).
* `tests/`: модульные и golden-тесты.

## Ключевые архитектурные решения (почему так, а не иначе)

1. **Потоковое чтение через генераторы вместо `read()` и `readlines()`**. Генераторы читают файлы построчно и не загружают весь текст в оперативную память. Это позволяет обрабатывать гигабайтные выгрузки при минимальном потреблении RAM.
2. **`csv.reader` вместо `csv.DictReader` для заказов**. В реальных данных встречаются строки, где меньше 8 колонок. `csv.reader` позволяет дополнить недостающие поля пустыми строками `""` и сохранить исходный вид записи для файла `rejected.csv`.
3. **`Decimal` с округлением `ROUND_HALF_UP` для каждого заказа**. Тип `float` даёт погрешности двоичного представления дробей. Перевод каждого заказа в рубли через `Decimal` с немедленным округлением до копеек гарантирует точность финансовых расчётов.
4. **Проверка цифр через регулярные выражения `^[0-9]+$` вместо `.isdigit()`**. Стандартный метод `str.isdigit()` в Python возвращает `True` для не-ASCII символов, например арабской цифры `٣` в строке 83. Регулярное выражение пропускает строго ASCII-цифры.
5. **Метод двух указателей (sliding window) для поиска `suspicious_users`**. Сортировка времён заказов пользователя и проход двумя указателями находят максимум в окне 600 секунд за `O(K log K)` вместо квадратичного перебора всех пар `O(K^2)`.
6. **Явный словарь английских месяцев `MONTH_MAP` при разборе логов**. Формат `%b` в `strptime` зависит от локали операционной системы и падает на русской локали при чтении `Jun` или `May`. Явный словарь работает одинаково в любом окружении.
7. **Декодирование логов с параметром `errors="replace"`**. В логах встречаются битые байты вне стандарта UTF-8. Замена повреждённых байтов на символ `U+FFFD` защищает процесс от падения с `UnicodeDecodeError` и позволяет разобрать строку, если она подходит под формат.
8. **Контекст-менеджер `RejectedCsvWriter`**. Записывает отклонённые заказы на диск сразу в процессе чтения файла без накопления списка ошибок в памяти и гарантированно закрывает дескриптор файла при выходе из блока.

## Что я нашёл в данных

### 1. Выгрузка заказов (`orders.csv`: 50 000 записей)
* **Валидных записей (`rows_valid`)**: 46 984.
* **Отклонено записей (`rows_rejected`)**: 3 016 по 7 причинам:
  * `invalid_amount` (724 записи): нулевые и отрицательные суммы, текст, точка как разделитель тысяч. Пример: строка 53 (`ORD-985434`, сумма `0`).
  * `invalid_date` (528 записей): несуществующие даты в календаре, час `24:00:00`, даты без ведущих нулей. Примеры: строка 32 (`31.02.2026 10:00`), строка 83 (`2026-03-05T24:00:00`).
  * `invalid_order_id` (456 записей): строчные буквы в префиксе `ord-`, неверная длина номера. Пример: строка 157 (`ORD-1234567` из 7 цифр).
  * `unknown_status` (404 записи): неразрешённые названия статусов. Пример: строка 107 (`ORD-158236`, статус `cancel`).
  * `invalid_user_id` (385 записей): нулевой ID, пробелы внутри числа, текст. Пример: строка 32 (`ORD-126045`, значение `"1 2"`).
  * `unknown_currency` (269 записей): пустая валюта или код вне справочника `rates.json`. Пример: строка 66 (`ORD-169153`, пустая строка `""`).
  * `invalid_items_count` (250 записей): пустые поля, ноль, отрицательные числа, не-ASCII цифры. Примеры: строка 58 (пустое поле `""`), строка 83 (арабская цифра `٣`), строка 157 (`-1`).
* **Дубликаты заказов (`duplicates_replaced`)**: 3 004 валидные записи были вытеснены более поздними записями с тем же `order_id`. Уникальных заказов осталось 43 980.
* **Форматирование городов и сумм**: названия городов содержат лишние пробелы, разный регистр и синонимы (`Moscow`, `г. Москва`, `уфа`), а в 1 123 уникальных заказах выручки город не заполнен (категория `Не указан`). В суммах встречаются пробелы, неразрывные пробелы `\u00a0` и запятые (`13 134,48`).
* **Подозрительные пользователи (`suspicious_users`)**: найдено 44 пользователя (ID от `20001` до `20062`), оформивших от 5 до 12 уникальных заказов за 10 минут. Максимум в 12 заказов за окно показали пользователи `20003`, `20005`, `20018`, `20021`, `20023` и `20028`.

### 2. Логи веб-сервера (`access.log`: 100 000 строк)
* **Успешно разобрано (`lines_parsed`)**: 99 350 строк.
* **Битые строки (`lines_malformed`)**: 650 строк. Включают пустые строки, нестандартные HTTP-методы, коды ответа вне диапазона 100-599, невозможные даты, обрезанные записи и строки с лишними токенами в хвосте. Также присутствуют битые UTF-8 байты.
* **Классы статусов и ошибки**: `2xx`: 91 515, `3xx`: 2 077, `4xx`: 4 991, `5xx`: 767. Доля серверных ошибок `5xx` составляет `0.77%`.
* **Производительность эндпоинтов**: самый нагруженный эндпоинт `GET /api/v1/orders/{id}` (14 649 запросов, p50 `0.070` с, p95 `0.161` с, p99 `0.239` с). Самые медленные запросы в топ-10: `GET /api/v1/search` (p95 `1.200` с, p99 `2.223` с) и `POST /api/v1/orders` (p95 `0.826` с, p99 `1.399` с).
* **Brute-force атаки (`bruteforce_ips`)**: обнаружено 19 IP-адресов, получивших от 20 до 50 ответов `401` за одну календарную минуту. Лидеры по числу попыток: `193.220.43.250` (50 в минуту), `45.32.135.80` (40 в минуту), `185.9.184.248` (35 в минуту).

## Ограничения и что улучшил бы

1. **Дедупликация при десятках миллионов заказов**. Сейчас уникальные заказы хранятся в словаре в оперативной памяти. Для файлов на десятки гигабайт стоит перенести индекс дедупликации во временную БД `sqlite3` на диске.
2. **Память под расчёт перцентилей времени ответа**. Утилита сохраняет список значений `Decimal` для каждого эндпоинта. Так как время в логах записано с точностью до миллисекунд (3 знака после точки), списки можно заменить на гистограмму частот `Counter[Decimal]`. Это сократит расход памяти с `O(N)` до константы.
